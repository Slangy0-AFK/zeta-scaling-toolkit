Suspension preserves the process's in-memory state only while the machine
and process remain alive, and continues to consume RAM. A Codespace stop,
rebuild, or deletion can terminate it; the checkpoint is the durable fallback.
The checkpoint may precede the exact in-memory state by a few tokens because
the pause follows the checkpoint write.

## Resuming

**Never launch a second 100K runner while the suspended process exists.**
Check both PID identity and the `T` process state before continuing the same
process. If they match and continuation is desired:

```bash
ps -p 35538 -o pid,stat,args
# Verify /proc/35538/stat start time is still 577769 before sending SIGCONT.
kill -CONT 35538
```

The runner's 12-hour wall-time budget includes time spent suspended; a long
pause can exhaust it, and recorded throughput after continuation can include
the paused time. Start a fresh passive monitor with a new log path as described
in the experiment's [quickstart](../context-100k-experiment-v2/QUICKSTART.md).

If the original process no longer exists, verify the checkpoint hash, pinned
model and tokenizer, input stream, available memory, and latest
`progress.jsonl` first. Then use the existing resume mechanism, for example
the tmux launcher in the quickstart. The launcher lock does not detect the
older unmanaged process: independently ensure no other runner is active.
Resume loads the latest progress checkpoint and continues from its recorded
position; tokens beyond that checkpoint, if any, must be processed again.
End-to-end resume equivalence has not been independently demonstrated.

The pinned model cache and Python environment live outside Git and are not
included in the checkpoint backup. Later, newly created checkpoints will not
automatically be pushed.
